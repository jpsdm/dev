## Sub-project — Active bin directory exposure (final review)

Final whole-branch review: 2026-09-30, `docs/superpowers/plans/2026-09-30-active-bin-dir-exposure.md`.

**Obsoleted — `internal/activebin` and the mechanism it supported were removed by the shell-function-path-management redesign (2026-10).** The entries below are kept for historical reference only; none of them is actionable against the current codebase.

- **Go's `BinDir` does not expose `go install`-built binaries.** `BinDir` returns `<versionDir>/bin`, which only ever holds `go`/`gofmt` — `go install` writes to `GOBIN` or `$GOPATH/bin` (typically `~/go/bin`), never into a managed version's own directory. This is an explicit, pre-existing non-goal of the Go provider (`docs/superpowers/specs/2026-09-29-go-provider-design.md`), not something this feature could close without GOPATH/GOBIN management it was never scoped to add. The incorrect claim that `go install` binaries become reachable was removed from `Runtime.BinDir`'s doc comment and the README as part of the final-review fix wave; this entry just records the underlying limitation for future reference.
- `internal/activebin/activebin_unix.go`'s `Repoint` leaves an orphan `<linkPath>.new` symlink behind if the final `os.Rename` fails (on top of the already-deferred fixed-temp-name collision risk from Task 3's review). Low likelihood, same risk class already accepted.
- `activebin.Repoint` fails with `ENOTEMPTY` if `active/<lang>` happens to be a real non-empty directory rather than a link (should never happen given this design always creates it as a link, but untested), and `Create` silently no-ops on an existing *broken* link (dangling target) rather than detecting and repairing it. Both are adjacent to, and intentionally outside, the spec's explicitly out-of-scope "manually deleted version directory" case.
- `internal/activebin`'s package doc comment lives only in `activebin_unix.go` (guarded by `//go:build !windows`), so a Windows-only build has an undocumented package from `go doc`'s perspective. Cosmetic.
- `cmd/setup.go`'s `installShims` still constructs its own `devruntime.NewManager()` + `providers.Register(m)` rather than reusing the same file's `langManager` (used elsewhere in `cmd/setup.go`/`cmd/env.go` for `ExportLines`'s new `langs` parameter) — two sources of truth for "the registered provider list" in the same file. Pre-existing pattern in `installShims` that this plan didn't introduce, but the new `langManager` usage nearby makes the inconsistency more visible now.
- README's new "As of this release" phrasing (now rewritten by the final-review fix wave) will read oddly once another release ships — worth revisiting wording in a future doc pass, not urgent.
- `internal/activebin/activebin_windows_test.go`'s assertion that `os.Lstat(junction).Mode()&os.ModeSymlink != 0` depends on a Go-toolchain behavior (junctions reported as `ModeSymlink` since Go 1.15) that cannot be verified without a real Windows host — flagged, not actionable here.

## Pre-existing — `Uninstall` can leave `active/<lang>` dangling on a marker-removal error

Task review: 2026-09-30, branch `feat/active-bin-dir-exposure` (active-bin-dir-exposure plan, Task 5).

- In each provider's `Uninstall`, `os.RemoveAll(destDir)` runs unconditionally before the active-version branch. If the subsequent `os.Remove(markerPath)` then fails with a real (non-`IsNotExist`) error, `Uninstall` returns before ever reaching `activebin.Repoint`, leaving `active/<lang>` dangling — pointing at the now-deleted version's bin directory — instead of reverted to the placeholder. This ordering predates Task 5's diff (the marker-removal-then-return-early shape already existed for the `current/<lang>` marker before this plan added the repoint step); Task 5 just inherited it. Not one of the plan's three named Review Focus risks, so not a blocker — recorded here for visibility.

## Bugfix — `dev update` shim refresh uses a stale provider list

Code review: 2026-09-30, branch `fix/update-shim-refresh-uses-old-binary`.

- **No self-heal for shims that are already missing or hand-deleted.** `dev lang install`/`dev lang use`/`dev lang activate` never touch `$DEV_HOME/bin` — shims are only ever (re)created by `cmd/setup.go`'s `installShims` (via `dev setup` or the hidden `__refresh-shims` command `dev update` now spawns). A user who filed the original report is running a pre-fix `dev` binary; their *next* `dev update` still takes the corrected path and will properly pick up any provider added in that release, but if a *future* release adds another provider while they're several versions behind, or if `$DEV_HOME/bin` is hand-edited/cleaned, there's still no automatic recovery short of manually running `dev setup` again. Having `dev lang install`/`activate` ensure the target provider's own shims exist would close this permanently. Deliberately out of scope for the shim-refresh-after-update fix itself.

## Design limitation — Python's pip console-scripts remain unreachable on Windows

Task review: 2026-09-30, branch `feat/active-bin-dir-exposure` (active-bin-dir-exposure plan, Task 1).

- **`internal/runtime/python.(*Python).BinDir` returns the version root on Windows, not `Scripts/`.** The whole point of this plan is exposing a language's active-version bin directory on `PATH` so tools installed by that language's own package manager (here, `pip install`'d console-scripts) are reachable without `dev` knowing their names in advance. On Windows, Python's `python.exe`/`python3.exe` live at the version root, while pip-installed console-scripts land in `Scripts/` instead — `BinDir` can only return one directory, and it must be the root, because once a version is active, `python`/`python3` resolve via the `active/python` `PATH` entry with no shim fallback — pointing `BinDir` at `Scripts/` would break the basic `python` command working after activation, which is far worse than the gap it would close. (python-build-standalone's Windows builds also ship no `pip` executable at all today, so `Scripts/` is empty regardless, for now.) Properly supporting both directories would need `BinDir` (and the whole exposure mechanism) to support more than one directory per language — out of scope for this plan, since no other provider needs it. Revisit if PBS ever ships `pip` on Windows and this becomes a real complaint.
